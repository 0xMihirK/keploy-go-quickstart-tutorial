<Slide id="how-it-works">
<Lesson>

Writing API tests by hand means writing fakes: an interface for the database, a mock that implements it, fixtures for each case. Keploy records them for you. It runs your app unchanged and sits on the network between the app and everything it talks to.

While you **record**, every request and response becomes a test case, and every database call and its answer becomes a mock. When you **test**, Keploy starts the app, sends the recorded requests, and answers the database calls from the mocks.

On Linux, Keploy uses eBPF, a kernel feature that can reroute a program's network traffic, to pass your app's connections through its proxy, without changes to your code.

Keploy connects to a free Keploy account. After you record, Keploy uploads the mocks to it, and a CI job can later fetch them with an API key from the same account.

1. Create an account at [app.keploy.io](https://app.keploy.io) and stay signed in there.
2. Run the login command:

   ```bash
   keploy login
   ```

3. Keploy opens a sign-in page in your browser. If it can't, as in a WSL terminal, it prints the link instead; open it in the browser where you're signed in.
4. Approve the sign-in. The link works for about a minute, so do it right away.

The terminal then prints `Logged in successfully!` and your plan, `You are on the Keploy Free plan.` The `mcp-install` lines after that are optional; they connect Keploy to AI coding agents, which <GoTo id="ai-agents">a later page</GoTo> covers. On a machine with no browser at all, `keploy login --manual-login` gives you a manual login prompt instead of opening one.

<Slide id="clone">
<Lesson>

This follows the **Running App Locally** path from Keploy's quickstart. The Go app runs on your machine, and only MongoDB runs in Docker, from the sample's own compose file.

```bash title="Clone the sample"
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
go mod download
rm -rf keploy
```

`go mod download` fetches the dependencies now, so the first `go run` starts quickly. `rm -rf keploy` removes the sample's example recordings, so every test you replay is your own.

```bash title="Start MongoDB"
docker network create keploy-network
docker compose up -d mongo
```

The sample's compose file expects a Docker network named `keploy-network`; if Docker says it already exists, carry on. `-d` keeps MongoDB running in the background. Compose also prints a warning that the `version` attribute is obsolete; it's harmless. If `docker` says `permission denied` on Linux, run `sudo usermod -aG docker $USER` and open a new shell.

```bash title="Point the app at local MongoDB"
sed -i 's/mongoDb:27017/localhost:27017/' main.go
```

`mongoDb:27017` (line 35 of `main.go`) only resolves inside Docker. The app runs on your machine, so `sed` points it at `localhost`. This edit is only for running the sample outside Docker; Keploy itself needs no code changes.

<Slide id="record">
<Lesson>

`keploy record -c` starts your app with the command you give it and records everything that crosses the network. Open a second terminal for later. In the first one, still in `samples-go/gin-mongo`:

```bash title="Terminal 1"
keploy record -c "go run main.go handler.go"
```

When you record as a normal user, Keploy asks for your sudo password, because its agent needs root to attach eBPF hooks to your app's network traffic. Wait for `Started ingress forwarding`, which means Keploy is listening on port 8080. Then, in the second terminal:

```bash title="Terminal 2"
curl --request POST \
  --url http://localhost:8080/url \
  --header "content-type: application/json" \
  --data '{"url": "https://keploy.io"}'

curl -i http://localhost:8080/7fvpSsFg
```

The first request creates a short link and the second follows it. The code is a hash of the URL, so you get the same `7fvpSsFg` shown here. `-i` prints the response headers, so you see the `303` status and the `Location` header pointing at keploy.io.

Stop with **Ctrl+C** in the first terminal.

<Callout type="tip" title="Press Ctrl+C once">

Keploy then replays the new tests to check for noise, writes `mappings.yaml`, and uploads `mocks.yaml` to your Keploy account, which is where CI fetches it later. A second Ctrl+C skips all of that, so wait for Keploy to exit.

</Callout>

<Callout type="info" title="If a request doesn't go through">

`curl: (7) Failed to connect` means Keploy isn't listening yet: wait for `Started ingress forwarding` and send it again. If Keploy reports `address already in use`, something else holds port 8080; `docker ps --filter publish=8080` shows a container using it.

</Callout>

<Slide id="replay">
<Lesson>

Stop MongoDB first, so the only thing that can answer the app's queries is Keploy's mocks:

```bash
docker compose stop mongo
keploy test -c "go run main.go handler.go" --delay 10
```

`--delay 10` gives the app 10 seconds to start before Keploy sends requests. `go run` compiles first and the sample sleeps two seconds before connecting, so the default of 5 can be too short.

Both tests pass with no database running. When the app connected and queried, Keploy's proxy answered from `mocks.yaml`.

<Slide id="break">
<Lesson>

Passing tests only mean something if they fail when behavior changes. Change the redirect's status code on line 66 of `handler.go` and replay:

```diff title="handler.go, line 66"
- c.Redirect(http.StatusSeeOther, u.URL)
+ c.Redirect(http.StatusMovedPermanently, u.URL)
```

```bash
sed -i 's/StatusSeeOther/StatusMovedPermanently/' \
  handler.go
keploy test -c "go run main.go handler.go" --delay 10
git checkout handler.go
```

Keploy prints a table for each failure: recorded `303`, now `301`. Browsers cache a `301` and keep sending visitors to the cached target; they don't cache a `303`. The last command puts the code back.

<Slide id="noise">
<Lesson>

Some values differ on every run however correct your code is: timestamps, generated IDs, the `Date` header. Keploy calls them **noise** and skips them when it compares responses.

The switch replays the test with and without the `body.ts` rule in `post-url-1.yaml`. Without the rule the test fails on `ts` alone, even though the short URL still matches.

To try it yourself (optional), back up the test, delete the rule, replay, and restore the file:

```bash
cp keploy/test-set-0/tests/post-url-1.yaml \
  /tmp/post-url-1.yaml
sed -i '/body.ts: \[\]/d' \
  keploy/test-set-0/tests/post-url-1.yaml
keploy test -c "go run main.go handler.go" --delay 10
cp /tmp/post-url-1.yaml \
  keploy/test-set-0/tests/post-url-1.yaml
```

When your own endpoints return timestamps or IDs, set the rule once for the whole project:

```yaml title="add to keploy.yml"
test:
    globalNoise:
        global:
            body:
                ts: []
```

An empty list means "ignore this field, whatever its value". With the rule in `keploy.yml` instead of the test file, both tests still pass.

</Lesson>

<Slide id="ai-agents">
<Lesson>

Keploy hosts an MCP server at `api.keploy.io`. MCP is the protocol coding agents use to call outside tools, so with it an agent such as Claude Code can create and run Keploy tests when you ask it to. `keploy mcp-install` creates an access token (a PAT) for your Keploy account and adds the server to the agent's config, so sign in first (step 2).

```bash title="Claude Code"
keploy mcp-install --editor claude-code
```

`--editor` also takes `cursor`, `windsurf`, `claude-desktop`, `codex`, `antigravity` and `github-copilot`. For Antigravity, Keploy writes `~/.gemini/antigravity/mcp_config.json`. `--all` sets up every agent it finds on the machine except GitHub Copilot, which keeps no config file; for Copilot, `--editor github-copilot` prints blocks to paste into VS Code, JetBrains or Visual Studio.

The agent tests the running app, so start it first: `docker compose start mongo`, then `go run main.go handler.go` in another terminal. Quit and reopen the agent so it loads the server, then ask it:

```text title="Ask the agent"
generate Keploy API tests for this service.
```

The agent reads your code, calls Keploy's tools to generate test suites for each endpoint, runs them against your app and reports back. The suites and their report are in your Keploy account.

### OpenCode

OpenCode isn't on `mcp-install`'s list, so add the server to `opencode.json` in your project. The file reads the key from an environment variable, so the key itself never lands in your repository:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "keploy": {
      "type": "remote",
      "url": "https://api.keploy.io/client/v1/mcp",
      "headers": {
        "Authorization": "Bearer {env:KEPLOY_API_KEY}"
      }
    }
  }
}
```

Create an API key at [app.keploy.io](https://app.keploy.io), set it with `export KEPLOY_API_KEY=` before you start `opencode`, and ask the same question.

<Callout type="info" title="One token per account">

On the same machine, `mcp-install` reuses the token saved in `~/.keploy/mcp.yaml`, so agents you already set up keep working. On another machine it creates a new token and revokes the old one, and agents still holding the old token get a 401 error. `keploy mcp-install --rotate --editor <name>` creates a fresh token on the machine where you need it.

</Callout>

No agent? `keploy status` shows where you are and the next step, in any terminal.
