<Lesson>

Keploy watches the requests your Go app handles and the database calls it makes, and saves both as YAML. Replay that file later and your app gets the same answers, even with the database switched off.

It takes about 15 minutes. Every step has a practice terminal that replays my real run, so you can try each command here before you run it yourself.

<Slide id="how-it-works">
<Lesson>

API tests for a Go service usually need fakes: an interface for the database, a mock that implements it, fixtures for each case. Keploy skips that. It runs your app unchanged and sits on the network between the app and everything it talks to.

While you **record**, every request and response becomes a test case, and every database call and its answer becomes a mock. When you **test**, Keploy restarts the app, sends the recorded requests, and answers the database calls from the mocks.

On Linux, Keploy uses eBPF, a kernel feature that can reroute a program's network traffic, to pass your app's connections through its proxy. That's how it works without changes to your code.

<Slide id="record">
<Lesson>

`keploy record -c` runs your app's start command and records everything that crosses the network. You need two terminals: one for Keploy, one to send requests.

Wait for `Started ingress forwarding` in the first terminal. It means Keploy is listening on your app's port. Then send the two requests: the first creates a short link, the second follows it. The code is a hash of the URL, so you'll get the same <Stack only="gin" inline>`7fvpSsFg`</Stack><Stack only="echo" inline>`4KepjkTT`</Stack> I did.

Stop with **Ctrl+C**. Keploy then replays what it just recorded to check the tests are stable before it exits.

<Callout type="warning" title="Sending requests from PowerShell?">

In Windows PowerShell 5.1, `curl` means `Invoke-WebRequest` and fails with `A positional parameter cannot be found that accepts argument 'POST'`. Use your WSL2 terminal, or `curl.exe`.

</Callout>

<Lesson>

Recording left a `keploy/` folder next to your code. Click through the files; they're the real ones from my run, and underlined lines have notes.

- **Keploy added noise rules by itself.** The response's `ts` timestamp and the `Date` header change on every run, so Keploy ignores them when comparing. <GoTo id="noise">See what happens without them</GoTo>.

<Slide id="break">
<Lesson>

Passing tests only mean something if they fail when behavior changes. Change the redirect's status code and replay:

<Stack only="gin">

```diff title="handler.go, line 66"
- http.StatusSeeOther
+ http.StatusMovedPermanently
```

Keploy prints a table for each failure: recorded `303`, now `301`. Browsers cache a `301` and keep sending people to the old target after the link changes; a `303` isn't cached.

</Stack>

<Stack only="echo">

```diff title="handler.go, line 168"
- http.StatusPermanentRedirect
+ http.StatusTemporaryRedirect
```

The app runs as a compiled binary, so rebuild it with `go build -o echo-psql-url-shortener .` before you replay.

Keploy prints a table for each failure: recorded `308`, now `307`. Browsers cache a `308` and keep sending people to the old target after the link changes; a `307` isn't cached.

</Stack>

Undo the change with `git checkout handler.go`<Stack only="echo" inline>, then rebuild</Stack>.

<Slide id="noise">
<Lesson>

Some values differ on every run however correct your code is: timestamps, generated IDs, the `Date` header. Keploy calls them **noise** and skips them when it compares responses.

Flip the switch to delete the `body.ts` rule and replay. That's what I did: without the rule the test fails on `ts` alone, even though the short URL still matches.

When your own endpoints return timestamps or IDs, set the rule once for the whole project in `keploy.yml`:

```yaml title="keploy.yml"
test:
    globalNoise:
        global:
            body:
                ts: []
```

An empty list means "ignore this field, whatever its value". I checked it on the Gin app: with the rule removed from the test file and added here, both tests pass.

</Lesson>

<Slide id="next" layout="single">

- **Run it in CI.** Commit `keploy/`; the generated `.gitignore` already leaves out mocks and reports. In CI, set `KEPLOY_API_KEY`, install Keploy and run the same `keploy test` command. Keploy downloads the mocks by the hash in `config.yaml`.
- **Record more cases.** Run `keploy record` again and send other requests, such as an unknown short code that returns 404. Each run adds a test set.
- **Try your own service.** Nothing here is specific to the sample. Point `keploy record -c` at the command that starts your app.
- **Read the reference.** [Keploy's docs](https://keploy.io/docs/) cover configuration and other languages, and the [Go samples](https://github.com/keploy/samples-go) include gRPC, MySQL and Redis apps.
