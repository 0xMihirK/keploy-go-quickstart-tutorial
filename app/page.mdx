<Slide id="overview">
<Lesson>

Keploy watches the requests your Go app handles and the database calls it makes, and saves both as YAML. Replay those files later and your app gets the same answers, even with the database switched off.

It takes about 15 minutes. Most steps have a practice terminal that plays back my real run, so you can watch each command, or type it yourself, before you run it on your machine.

<Slide id="how-it-works">
<Lesson>

API tests for a Go service usually need fakes: an interface for the database, a mock that implements it, fixtures for each case. Keploy skips that. It runs your app unchanged and sits on the network between the app and everything it talks to.

While you **record**, every request and response becomes a test case, and every database call and its answer becomes a mock. When you **test**, Keploy restarts the app, sends the recorded requests, and answers the database calls from the mocks.

On Linux, Keploy uses eBPF, a kernel feature that can reroute a program's network traffic, to pass your app's connections through its proxy, without changes to your code.

<Slide id="clone">
<Lesson>

This is the **Running App Locally** path from Keploy's quickstart: the Go app runs on your machine, not in a container. Only MongoDB runs in Docker, from the sample's own compose file.

```bash
git clone https://github.com/keploy/samples-go.git && cd samples-go/gin-mongo
go mod download
rm -rf keploy
docker compose up -d mongo
sed -i 's/mongoDb:27017/localhost:27017/' main.go
```

- `go mod download` fetches the dependencies now. Without it, the first `go run` spent over two minutes downloading before the app started.
- `rm -rf keploy` removes recordings that ship with the sample, made by an older Keploy, so every test you replay is your own.
- The docs say to change MongoDB's address on line 21 of `main.go`; in the current sample it's line 35. `mongoDb:27017` only resolves inside Docker, so `sed` points it at `localhost`.

If Compose says the `keploy-network` network is missing, create it with `docker network create keploy-network`. Keploy's installer usually makes it when Docker is running.

<Slide id="record">
<Lesson>

`keploy record -c` starts your app with the command you give it and records everything that crosses the network. Open two terminals. In the first:

```bash
keploy record -c "go run main.go handler.go"
```

Keploy restarts itself with `sudo`, so it asks for your password: hooking the app's network traffic needs root. Wait for `Started ingress forwarding`, which means Keploy is listening on port 8080. Then, in the second terminal:

```bash
curl --request POST --url http://localhost:8080/url --header "content-type: application/json" --data '{"url": "https://keploy.io"}'
curl -i http://localhost:8080/7fvpSsFg
```

The first request creates a short link and the second follows it. The code is a hash of the URL, so you'll get the same `7fvpSsFg` I did.

Stop with **Ctrl+C** in the first terminal. Keploy then replays what it just recorded to check the tests are stable before it exits.

<Callout type="warning" title="Sending requests from PowerShell?">

In Windows PowerShell 5.1, `curl` means `Invoke-WebRequest` and fails with `A positional parameter cannot be found that accepts argument 'POST'`. Use your WSL2 terminal, or `curl.exe`.

</Callout>

<Slide id="inspect">
<Lesson>

Recording left a `keploy/` folder next to your code. Click through the files; they're the real ones from my run, and underlined lines have notes.

- **Keploy added noise rules by itself.** The response's `ts` timestamp and the `Date` header change on every run, so Keploy ignores them when comparing. <GoTo id="noise">See what happens without them</GoTo>.
- **The mocks don't go in git.** The generated `keploy/.gitignore` excludes `mocks.yaml`. Keploy uploaded the mocks to your account, and `config.yaml` holds the hash CI uses to fetch them.

<Slide id="replay">
<Lesson>

Keploy's docs stop at running the tests. I stopped MongoDB first, to see whether the mocks really stand in for it:

```bash
docker compose stop mongo
keploy test -c "go run main.go handler.go" --delay 10
```

`--delay 10` gives the app 10 seconds to start before Keploy sends requests. `go run` compiles first and the sample sleeps two seconds before connecting, so the default of 5 can be too short.

Both tests pass with no database running. When the app connected and queried, Keploy's proxy answered from `mocks.yaml`.

<Slide id="break">
<Lesson>

Passing tests only mean something if they fail when behavior changes. Change the redirect's status code on line 66 of `handler.go` and replay:

```diff title="handler.go"
- c.Redirect(http.StatusSeeOther, u.URL)
+ c.Redirect(http.StatusMovedPermanently, u.URL)
```

```bash
sed -i 's/StatusSeeOther/StatusMovedPermanently/' handler.go
keploy test -c "go run main.go handler.go" --delay 10
git checkout handler.go
```

Keploy prints a table for each failure: recorded `303`, now `301`. Any change of status code changes what clients do; here, browsers start caching the redirect, because they cache a `301` and don't cache a `303`. The last command puts the code back.

<Slide id="noise">
<Lesson>

Some values differ on every run however correct your code is: timestamps, generated IDs, the `Date` header. Keploy calls them **noise** and skips them when it compares responses.

Flip the switch to delete the `body.ts` rule and replay. That's what I did: without the rule the test fails on `ts` alone, even though the short URL still matches.

When your own endpoints return timestamps or IDs, set the rule once for the whole project in `keploy.yml`:

```yaml title="keploy.yml"
test:
    globalNoise:
        global:
            body:
                ts: []
```

An empty list means "ignore this field, whatever its value". I checked it: with the rule removed from the test file and added here, both tests pass. If you deleted the line to try this, put it back or keep the `keploy.yml` rule.

</Lesson>

<Slide id="next" layout="single">

- **Run it in CI.** Commit `keploy/`; the generated `.gitignore` already leaves out mocks and reports. In CI, set `KEPLOY_API_KEY`, install Keploy and run the same `keploy test` command. Keploy downloads the mocks by the hash in `config.yaml`.
- **Record more cases.** Start MongoDB again with `docker compose start mongo`, run `keploy record` and send other requests, such as an unknown short code that returns 404. Each run adds a test set.
- **Try your own service.** Nothing here is specific to the sample. Point `keploy record -c` at the command that starts your app.
- **Read the reference.** [Keploy's docs](https://keploy.io/docs/) cover configuration and other languages, and the [Go samples](https://github.com/keploy/samples-go) include gRPC, MySQL and Redis apps.
