<Slide id="overview" layout="single">

Keploy turns real API traffic into tests. It records the requests your app handles and the database and API calls it makes, then replays them as tests with those dependencies mocked, with no changes to your code. Its core record-and-replay engine is open source under Apache 2.0.

<Slide id="how-it-works">
<Lesson>

Writing API tests by hand means writing fakes: an interface for the database, a mock that implements it, fixtures for each case. Keploy records them for you. It runs your app unchanged and sits on the network between the app and everything it talks to.

While you **record**, every request and response becomes a test case, and every database call and its answer becomes a mock. When you **test**, Keploy starts the app, sends the recorded requests, and answers the database calls from the mocks.

On Linux, Keploy uses eBPF, a kernel feature that can reroute a program's network traffic, to pass your app's connections through its proxy, without changes to your code.

<Slide id="sign-in">
<Lesson>

Keploy connects to a free Keploy account. After you record, Keploy uploads the mocks to it, and a CI job can later fetch them with an API key from the same account.

1. Create an account at [app.keploy.io](https://app.keploy.io) and stay signed in there.
2. Run the login command:

   ```bash
   keploy login
   ```

3. Keploy opens a sign-in page in your browser. If it can't, as in a WSL terminal, it prints the link instead; open it in the browser where you're signed in.
4. Approve the sign-in. The link works for about a minute, so do it right away.

The terminal then prints `Logged in successfully!` and your plan, `You are on the Keploy Free plan.` The `mcp-install` lines after that are optional; they connect Keploy to AI coding editors. On a machine with no browser at all, `keploy login --manual-login` gives you a manual login prompt instead of opening one.

<Slide id="clone">
<Lesson>

This follows the **Running App Locally** path from Keploy's quickstart. The Go app runs on your machine, and only MongoDB runs in Docker, from the sample's own compose file.

```bash
git clone \
  https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
go mod download
rm -rf keploy
docker network create keploy-network \
  2>/dev/null || true
docker compose up -d mongo
sed -i 's/mongoDb:27017/localhost:27017/' \
  main.go
```

- `go mod download` fetches the dependencies now. Without it, the first `go run` spent over two minutes downloading before the app started.
- `rm -rf keploy` removes the sample's example recordings, so every test you replay is your own.
- The sample's compose file expects a Docker network named `keploy-network` and won't create it. `docker network create` makes it; if it already exists, `2>/dev/null || true` hides the error.
- `-d` keeps MongoDB running in the background so you can reuse the terminal. Compose also prints a warning that the `version` attribute is obsolete; it's harmless. If `docker` says `permission denied` on native Linux, run `sudo usermod -aG docker $USER` and open a new shell.
- `mongoDb:27017` (line 35 of `main.go`) only resolves inside Docker. The app runs on your machine, so `sed` points it at `localhost`. This edit is only for running the sample outside Docker; Keploy itself needs no code changes.

<Slide id="record">
<Lesson>

`keploy record -c` starts your app with the command you give it and records everything that crosses the network. Open a second terminal for later. In the first one, still in `samples-go/gin-mongo`:

```bash
keploy record -c "go run main.go handler.go"
```

When you record as a normal user, Keploy asks for your sudo password (`[sudo] password for dev:` in my run), because its agent needs root to attach eBPF hooks to your app's network traffic. Wait for `Started ingress forwarding`, which means Keploy is listening on port 8080. Then, in the second terminal:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header "content-type: application/json" \
  --data '{"url": "https://keploy.io"}'

curl -i http://localhost:8080/7fvpSsFg
```

The first request creates a short link and the second follows it. The code is a hash of the URL, so you'll get the same `7fvpSsFg` I did. `-i` prints the response headers, so you see the `303` status and the `Location` header pointing at keploy.io.

Stop with **Ctrl+C** in the first terminal.

<Callout type="tip" title="Press Ctrl+C once">

Keploy then replays the new tests to check for noise, writes `mappings.yaml`, and uploads `mocks.yaml` to your Keploy account, which is where CI fetches it later. A second Ctrl+C skips all of that, so wait for Keploy to exit.

</Callout>

<Callout type="info" title="If a request doesn't go through">

`curl: (7) Failed to connect` means Keploy isn't listening yet: wait for `Started ingress forwarding` and send it again. If Keploy reports `address already in use`, something else holds port 8080; `docker ps --filter publish=8080` shows a container using it.

</Callout>

<Slide id="replay">
<Lesson>

Stop MongoDB first, so the only thing that can answer the app's queries is Keploy's mocks:

```bash
docker compose stop mongo
keploy test -c "go run main.go handler.go" \
  --delay 10
```

`--delay 10` gives the app 10 seconds to start before Keploy sends requests. `go run` compiles first and the sample sleeps two seconds before connecting, so the default of 5 can be too short.

Both tests pass with no database running. When the app connected and queried, Keploy's proxy answered from `mocks.yaml`.

<Slide id="break">
<Lesson>

Passing tests only mean something if they fail when behavior changes. Change the redirect's status code on line 66 of `handler.go` and replay:

```diff title="handler.go, line 66"
- c.Redirect(http.StatusSeeOther, u.URL)
+ c.Redirect(http.StatusMovedPermanently, u.URL)
```

```bash
sed -i \
  's/StatusSeeOther/StatusMovedPermanently/' \
  handler.go
keploy test -c "go run main.go handler.go" \
  --delay 10
git checkout handler.go
```

Keploy prints a table for each failure: recorded `303`, now `301`. Browsers cache a `301` and keep sending visitors to the cached target; they don't cache a `303`. The last command puts the code back.

<Slide id="noise">
<Lesson>

Some values differ on every run however correct your code is: timestamps, generated IDs, the `Date` header. Keploy calls them **noise** and skips them when it compares responses.

The switch replays my run with the `body.ts` rule deleted from `post-url-1.yaml`. Without the rule the test fails on `ts` alone, even though the short URL still matches.

To try it yourself (optional), back up the test, delete the rule, replay, and restore the file:

```bash
cp keploy/test-set-0/tests/post-url-1.yaml \
  /tmp/post-url-1.yaml
sed -i '/body.ts: \[\]/d' \
  keploy/test-set-0/tests/post-url-1.yaml
keploy test -c "go run main.go handler.go" \
  --delay 10
cp /tmp/post-url-1.yaml \
  keploy/test-set-0/tests/post-url-1.yaml
```

When your own endpoints return timestamps or IDs, set the rule once for the whole project:

```yaml title="add to keploy.yml"
test:
    globalNoise:
        global:
            body:
                ts: []
```

An empty list means "ignore this field, whatever its value". In my run with the rule removed from the test file and added to `keploy.yml`, both tests passed.

</Lesson>

<Slide id="next" layout="single">

- **Run the tests in CI.** Commit the `keploy/` folder, add an API key from app.keploy.io as the `KEPLOY_API_KEY` secret, install Keploy in the job and run the same `keploy test` command. CI fetches the mocks by the hash in `config.yaml`, so record and replay once locally first. See the [GitHub Actions](https://keploy.io/docs/ci-cd/github/) and [GitLab](https://keploy.io/docs/ci-cd/gitlab/) guides.
- **Record more cases.** Start MongoDB again with `docker compose start mongo`, run `keploy record` and send other requests, such as an unknown short code that returns 404. Each run adds a test set.
- **Mock the tests you already have.** `keploy mock record -c "go test ./..."` saves the database and HTTP calls your existing suite makes, and `keploy mock replay -c "go test ./..."` runs the suite again with those calls answered from the mocks. It works the same with pytest or jest. See [Mock your tests](https://keploy.io/docs/running-keploy/mock-your-tests/).
- **Generate unit tests.** Keploy's [PR agent](https://keploy.io/docs/running-keploy/utg-pr-agent/) writes unit tests on your pull requests and keeps only the ones that build, pass and raise coverage. It supports Go today, and JavaScript support is on the way.
- **Try your own service.** Point `keploy record -c` at the command that starts your app. Don't record production data, since tests and mocks store request and response bodies as they are; `keploy sanitize` removes sensitive data from test cases.
- **Explore other stacks.** Keploy's [quickstarts](https://keploy.io/docs/quickstart/quickstart-filter/) cover Python, Java, JavaScript and C#, and the [Go samples](https://github.com/keploy/samples-go) include gRPC, MySQL and Redis apps.
